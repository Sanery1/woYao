# BM25：搜索结果为什么这样排？

- **Skill 版本：** woYao v0.19.0-preview.5（仓库提交 `d9d8776`）
- **研究日期：** 2026-11-25

面向会编程、还没学过搜索排序的读者。本文讲单个文本字段中的词法相关性，采用公开公式和合成数据；算例已用 Python 实际复算，没有启动 Elasticsearch，也没有运行真实检索质量评测。

你在公司文档库搜索“缓存失效”。一篇简短的故障说明排在前面，一份反复提到“缓存”的长文却排在后面：搜索引擎究竟在奖励什么？先把这一次排序算完，再看这些规则为什么有用，以及遇到错误排序时应该改哪里。

## 1. 先把一次搜索走到底

计算机首先要知道“缓存失效”里有哪些可以匹配的词。我们暂时约定，它会被拆成“缓存”和“失效”两个词，文档也按同样约定拆词。拆出的单位叫 **token**：它可以是一个词，也可以是一个字或子词，取决于实际分析器。这里直接给出拆词后的统计，避免把分词问题和打分问题同时引入。

下面是我们虚构的整个文档库。长度是 token 数，词频是某个词在这一篇中出现的次数。例如 D3 很长，包含三次“缓存”、两次“失效”；D1 较短，两词各出现一次。六篇文档合计 48 个 token，平均长度为 8。

| 文档 | 内容角色 | 长度 | “缓存”次数 | “失效”次数 |
| --- | --- | ---: | ---: | ---: |
| D1 | 简短故障说明 | 4 | 1 | 1 |
| D2 | 缓存背景笔记 | 8 | 3 | 0 |
| D3 | 详细排障文档 | 16 | 3 | 2 |
| D4 | 顺带提及缓存的周报 | 4 | 1 | 0 |
| D5 | 一般缓存指南 | 8 | 1 | 0 |
| D6 | 其他主题说明 | 8 | 0 | 0 |

BM25 会给每个命中的查询词单独算贡献，再把贡献加起来。你可以先把它理解为三个问题：这个词在文档中出现了几次？它在整个文档库中有多常见？文档是不是因为特别长，才容易碰巧提到它？

这个例子中，“缓存”出现在五篇里，“失效”只出现在两篇里。因此，单独命中“缓存”提供的区分信息较少，命中“失效”更有区分价值。与此同时，D3 重复出现的词会继续加分，但每多一次带来的增益逐渐变小；它较长，还要接受长度调整。

按后文公式计算，结果如下。所有数字来自本次实际运行的 [复算脚本](./_work/calc/bm25.py)，是公式教学结果，不是某次 Elasticsearch 请求的返回值。

| 文档 | “缓存”贡献 | “失效”贡献 | 总分 |
| --- | ---: | ---: | ---: |
| D1 | 0.303175 | 1.294379 | 1.597554 |
| D3 | 0.312092 | 1.104957 | 1.417049 |
| D2 | 0.378969 | 0 | 0.378969 |
| D4 | 0.303175 | 0 | 0.303175 |
| D5 | 0.241162 | 0 | 0.241162 |
| D6 | 0 | 0 | 0 |

D1 的两个词都只出现一次，却胜过 D3。它命中了区分度较高的“失效”，而且这些命中集中在短文本里。D2 虽然把“缓存”写了三次，但只命中了这个常见词。这里已经可以看到，BM25 不是简单按关键词总次数排序。

真正的查询还要先决定哪些文档具备候选资格。如果查询要求“缓存”和“失效”必须都命中，D2、D4、D5 会被排除；如果允许任一词命中，它们才能参与排序。Elasticsearch 的普通 `text` 字段 `match` 查询先分析文本，默认按 `or` 组合词项，也可设置为 `and`。这是查询逻辑的职责，BM25 负责给可匹配的词项打分。[官方 match 查询说明](https://www.elastic.co/docs/reference/query-languages/query-dsl/query-dsl-match-query)

## 2. 词为什么越写越不值钱？

D2 把“缓存”写了三次。直觉上，它比只出现一次的文档更可能在认真讨论缓存；但写三百次也不该自动成为最佳答案。反复堆词的文档会利用线性计数，把真实有用的文章挤下去。

BM25 用一条逐渐变平的曲线处理这种现象，叫 **词频饱和**。在长度刚好等于平均长度时，本例使用的词频因子为：

$$
g(f)=\frac{f(k_1+1)}{f+k_1}
$$

这里的 $f$ 是某词在当前文档中的次数，$k_1$ 控制曲线变平的快慢。先固定 $k_1=1.2$，只改变次数：

| 次数 $f$ | 词频因子 $g(f)$ |
| ---: | ---: |
| 1 | 1.000000 |
| 2 | 1.375000 |
| 4 | 1.692308 |
| 8 | 1.913043 |

次数从一变二，增加了 0.375；从四变八，增加约 0.221。文档确实因为多次出现关键词而得分更高，但收益越来越小。本例曲线最终趋近于 $k_1+1=2.2$，不会无限增长。这些数值仍由同一个复算脚本产生。

想象把 D2 里的“缓存”继续复制：在文本长度被固定的这个局部实验里，词频贡献逐渐接近上限。实际复制文字也会增加长度，所以还要同时考虑下一节的长度调整。把两个变量分开看，才能知道排序变化来自哪一个因素。

## 3. 命中一个稀有词，为什么比命中常见词更有分量？

在我们的库里，“缓存”几乎篇篇都有，只凭它很难判断哪篇专门解决当前故障。“失效”出现得少，命中它会把范围缩得更多。BM25 用 **逆文档频率**（IDF）表达词在整个库中的区分度。它看的是“有几篇包含这个词”，而不是“这个词总共出现了几次”。

本文选择 Lucene 9.12.3 文档给出的非负 IDF 写法：

$$
\operatorname{IDF}(t)=\ln\left(1+\frac{N-df(t)+0.5}{df(t)+0.5}\right)
$$

$N$ 是参与统计的文档数，$df(t)$ 是包含词 $t$ 的文档数，$\ln$ 是自然对数。代入六篇文档，“缓存”的 $df=5$，得到约 0.241162；“失效”的 $df=2$，得到约 1.029619。D3 里“失效”出现两次，仍只为 $df$ 贡献一篇。分子分母里的 0.5 和外层加一使这个具体实现的权重保持平滑、非负。[Lucene 9.12.3 的 IDF 与平均字段长度定义](https://lucene.apache.org/core/9_12_3/core/org/apache/lucene/search/similarities/BM25Similarity.html)

这不是在说稀有词天然重要。一个罕见的无关编号也可能获得较高 IDF。它只表示：在当前词库里，这个词更能把文档区分开。判断查询是否表达了人的需求，仍需要分词、查询设计和最终相关性评测。把整库换成另一组文档，IDF 和分数也会变化，因此这里的总分不等于“答案正确概率”。

## 4. 长文为什么要打折？

回到 D3。它长 16 个 token，是平均长度的两倍。即便每篇都随机谈到几个主题，长文也有更多机会碰到查询词。长度调整尝试让“集中讨论”和“顺带提及”更容易区分。

先算一个长度因子：

$$
B(d)=(1-b)+b\frac{|d|}{\operatorname{avgdl}}
$$

$|d|$ 是当前文档长度，$\operatorname{avgdl}$ 是平均长度，$b$ 决定调整力度。取本例的 $b=0.75$，D1 的长度比为 $4/8$，所以 $B=0.625$；D3 的长度比为 $16/8$，所以 $B=1.75$。

把它放入完整的词频因子：

$$
g(f,d)=\frac{f(k_1+1)}{f+k_1B(d)}
$$

长度因子越大，分母越大，相同次数得到的贡献越小。固定某词出现三次、其他条件相同，长度为 4、8、16 时，因子依次约为 1.760000、1.571429、1.294118。你现在可以直接解释 D2 和 D3 的“缓存”列：两篇都出现三次，D3 更长，所以这一词贡献更低。

但长文也可能因为涵盖内容更全面而长，不能把所有长度差都当成冗余。原作者的综述区分了“说得啰嗦”和“覆盖更多主题”两种来源，并采用可调的软归一化。$b=0$ 关闭长度影响，$b=1$ 使用完整长度比；中间值在两种极端之间折中。[Robertson 与 Zaragoza，2009，§3.4.5—3.5](https://www.staff.city.ac.uk/~sbrp622/papers/foundations_bm25_review.pdf)

## 5. 把三部分接起来，复算一个结果

现在每个零件都有含义了。对查询中的词分别计算“整库区分度 × 当前文档词频因子”，最后求和：

$$
\operatorname{score}(q,d)=\sum_{t\in q}\operatorname{IDF}(t)\,
\frac{f(t,d)(k_1+1)}{f(t,d)+k_1\left(1-b+b|d|/\operatorname{avgdl}\right)}
$$

对 D1，两个查询词的次数都为一，长度因子为 0.625，所以共同的词频因子是 $2.2/(1+1.2\times0.625)=1.257143$。分别乘上 0.241162 与 1.029619，得到 0.303175 和 1.294379，相加就是第一节的 1.597554。对 D6，两个词都没命中，所以两项贡献都是零；现实查询通常不会把这个完全无命中的文档放进词法候选结果。

这份教学公式保留了常见的 $(k_1+1)$ 分子。Lucene 9.12.3 的实际源码使用省略该常数的等价排序形式，还涉及字段长度的编码与解码；因此不能拿表中的小数当成该版本的 `_score` 原样复现。在同一个固定参数、单字段、相同 boost 的简化比较中，去掉共同正数只会整体缩放分数，不会改变顺序。[Lucene 9.12.3 固定版本源码](https://raw.githubusercontent.com/apache/lucene/releases/lucene/9.12.3/lucene/core/src/java/org/apache/lucene/search/similarities/BM25Similarity.java)

复算命令是：

```sh
python _work/calc/bm25.py
```

脚本已经实际运行，原始输出保存在 [bm25.out](./_work/calc/bm25.out)。它只依赖 Python 标准库。你可以修改 D3 的长度或词频，观察总分和排名，先保持其他变量不变，再做联合变化；这样得到的是对公式的实验，不是线上效果证明。

## 6. k1 和 b：两个旋钮究竟改什么？

**$k_1$ 控制重复命中的额外价值。** 固定文档为平均长度，把词频从一改成四：$k_1=0.6$ 时因子从 1 变为约 1.391304，$k_1=1.2$ 时变为约 1.692308，$k_1=2$ 时变为 2。较大的 $k_1$ 让重复出现保持更强的区分作用；取零时，只要命中，其因子就相同，多写几次没有额外收益。这里讨论的是固定长度的比较，避免把参数影响和长短变化混在一起。

**$b$ 控制相同词频下长短文的差别。** 固定词频三次，$b=0$ 时短文和长文因子都约为 1.571429；$b=0.75$ 时分别约为 1.760000 和 1.294118；$b=1$ 时差距进一步扩大。提高 $b$ 会加强长度调整，降低 $b$ 会减弱它，并不是让所有文档统一加分或减分。

Elastic 官方文档列出的默认值是 $k_1=1.2$、$b=0.75$。默认值适合做起点，最终需要拿自己的查询和相关性判断来验证。若故障是查询词压根没命中，调这两个旋钮解决不了候选缺失；若长篇权威资料系统性被压低，才值得在固定分词和查询条件后比较不同长度调整。[Elasticsearch similarity 参数说明](https://www.elastic.co/docs/reference/elasticsearch/index-settings/similarity)

## 7. 中文检索：先别急着调公式

我们的例子提前约定了“缓存”和“失效”两个 token。真实中文没有天然空格：如果文档把一个术语分析成整体，查询却拆成不兼容的单位，原本相关的文本可能无法按预期匹配。分词还会改变词频、文档频率和长度，因此改变 BM25 的全部输入。

排查时先用 `_analyze` 看实际 token。下面只是给已有索引使用的请求示例，本次没有连接服务执行：

```http
POST /docs/_analyze
{
  "field": "body",
  "text": "缓存失效"
}
```

对查询文本、目标文档和容易误召回的文本分别检查，关注术语边界、大小写、停用词、同义词以及位置。`_analyze` 会返回分析后的 token，并允许从字段推导分析器；单纯观察请求字符串，无法知道实际匹配单位。[官方 Analyze API](https://www.elastic.co/docs/api/elasticsearch/operation/operation-indices-analyze)

中文分析器有多种选择。例如官方 Smart Chinese 插件支持中文及中英混合文本，会先分句再做词语切分。具体系统需要结合术语、数据和软件版本评测，不能从一个分词器名字直接推断质量。[Smart Chinese 官方说明](https://www.elastic.co/docs/reference/elasticsearch/plugins/analysis-smartcn)

如果两个词都命中，但不相关周报仍排得很高，再看查询是否需要更强的关系约束。普通词项打分不会自动要求“缓存”和“失效”紧挨着。`match_phrase` 使用位置来表达短语条件，默认 `slop=0`。它匹配的是分析后的 token 位置，而不是简单的原始字符串包含判断。[官方短语查询说明](https://www.elastic.co/docs/reference/query-languages/query-dsl/query-dsl-match-query-phrase)

最后用 `_explain` 检查具体文档为什么匹配、分数如何得到。这样能把“没被匹配”“匹配了但分低”“查询本来就允许不相邻的词”拆成不同问题，而不是统一归因于 BM25 不够聪明。[官方 Explain API](https://www.elastic.co/docs/api/elasticsearch/operation/operation-explain)

## 8. 从公式走向工程判断

BM25 处理的是词项证据。它擅长保留精确词项带来的区分信息：型号、错误码、专有名词通常能直接表达要求。反过来，如果用户说“数据没刷新”，文档只写“缓存失效”，双方没有可匹配词项，单靠本例公式无法建立语义关系。扩大词法匹配可以用受控的同义词或查询改写，也可以增加向量检索候选，再合并排序；Elastic 的混合搜索将全文和向量搜索组合为一个结果列表。[官方混合搜索说明](https://www.elastic.co/docs/solutions/search/hybrid-search)

如何判断应该改什么，可以沿本例逆推。先确认 D1、D3 这种人工认为相关的文档是否进入候选；没进入就检查分词和查询。候选足够但顺序不好，再查看词项贡献、长度、字段权重。只有发现排序误差确实和重复或长度有关，才把 $k_1$、$b$ 当成主要实验变量。调整一个变量时保留其他条件，记录哪些查询改善、哪些退步，避免用单条漂亮结果代替整体判断。

评测至少需要一组代表性查询和人工标注的相关文档。你可以观察前几条是否有用、相关文档是否被找回、用户是否能完成任务，同时记录响应耗时。本文没有给出某套参数在真实数据上的胜率，因为没有执行这样的实验；公式能解释机制，业务质量仍要靠真实样本检查。

## oOO!

回到“缓存失效”那次搜索：D1 胜过反复提到“缓存”的长文，来自三个可解释的选择——稀有词提供更多区分信息，重复命中的收益逐渐饱和，相同命中在长文里会被适度调整。它们一起让排序比简单数词更稳，但也保留了一个边界：词项匹配与长度统计无法独自理解人的完整意图。

所以你遇到错误排序时，已经可以先问“它到底匹配到了哪些 token”，再问“哪些贡献把分数推高”，最后才决定改查询、分词、长度调整，还是补充语义检索。BM25 的价值在于用便宜、可解释的词项统计提供一条基础排序路径；代价是你必须为它准备合适的匹配单位，并用自己的查询检验这些统计是否真的服务了需求。
