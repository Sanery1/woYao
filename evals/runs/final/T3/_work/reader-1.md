## 主线复述

恢复需要把业务事实、执行位置和操作身份从进程内存搬到耐久记录中。
LangGraph 主要按图状态和 checkpoint 继续，Temporal 主要通过事件历史重放编排。
外部动作成功而本地尚未确认时，恢复者仍可能再次发送请求。
稳定幂等身份、远端去重或查询协议负责避免重复业务效果，checkpoint 自身不能代替它们。
恢复边界越细越少重做，但也会增加持久化与调度成本，最终需要在真实崩溃窗口验证。

## 逐题回答

### 1. checkpoint 至少保存什么？

原回答：要保存继续做决策所需的业务输入及已经确认的结果、当前控制位置或下一步、已完成与未完成动作的状态和调用身份，以及解释这些数据的版本。采购例子还保存被批准的报价版本、批准对应关系、固定幂等键和订单结果；还要有稳定的运行或 thread 身份以找回同一任务。仅有 messages 不足，连接对象等可重新创建的进程资源也不是业务恢复状态。

支持：§3“业务输入”“控制位置”“已完成动作的结果”“未完成工具的调用身份”“版本”；§5“每次重启随机换 thread，又会找不到旧状态”。

### 2. 工具成功但 checkpoint 没写入就崩溃，会怎样？

原回答：新进程看到的还是旧状态，没有这次成功的确认，可能把工具步骤再执行一次。这不意味着第一次没有发生；若远端按原幂等键去重，就再次发送请求但拿回同一结果，若没有这种约束则可能重复创建订单。不能安全重试、又不能查询时，应将结果视为未知并核对。

支持：§2 时间线 D“Agent 本地无法仅凭 C 判断订单是否存在”；“网络层却可能发生了两次请求”；没有幂等或查询时“只能标记结果未知”。

### 3. checkpoint 为什么不能保证外部副作用恰好一次？

原回答：外部系统提交和本地 checkpoint 提交通常不是同一个事务，二者之间仍有崩溃窗口。先做动作后存会面临重复，先标完成后做动作会面临漏执行；即使同步 checkpoint，也没有把远端订单和本地状态合并成一次原子提交。恢复记录能决定从哪里继续，业务效果是否唯一还要由稳定身份和目标系统约束。

支持：§4“把顺序反过来……把重复风险换成丢执行风险”；§6“同步模式也没有把远端订单与 checkpoint 合成一个事务”；§10 区分函数尝试、网络投递和最终业务效果。

### 4. 给付款步骤设计防重复方案。

原回答：把报告的创建订单协议迁到付款：为同一笔业务付款生成并持久保存稳定 operation_id/幂等键及请求摘要，首次和重试都使用原键，真正的新付款才换键。执行前保存 prepared，付款服务必须按键去重并返回同一结果，同键不同金额等参数应报冲突；成功后保存外部付款号及 succeeded。超时或本地保存失败时保留原身份、视为 unknown，按原键查询或重试；若付款服务既不支持去重也不能查询，不能承诺自动防重复，应转人工核对。去重保留期还要覆盖流程可能重试的时间。

支持：§10 operations 表、request_hash、prepared/succeeded/unknown 及伪代码；“仅在 Agent 内记住……却没有远端去重，不能防止丢确认后的重复创建”；“幂等保留期短于流程最长重试期……假设就不成立”。这是报告订单示例的迁移，不是已验证付款实现。

### 5. 何时拆小步骤分别 checkpoint，代价是什么？

原回答：当一步包含昂贵计算、有副作用的动作，或等待外部输入，且希望恢复时复用前面已经完成的结果，就应考虑拆出独立恢复边界。比如报价、审批和创建订单各有独立价值；一大节点把它们包在一起，失败可能重跑前半段。代价是更多调度、持久记录、序列化、存储、提交延迟和结构复杂度，因此普通字符串拼接不值得同等级拆分。

支持：§4“昂贵或有副作用的动作拆成独立恢复单元，可以减少重做范围”；“代价是更多调度和持久化记录”；§9 大状态反复写入增加存储与序列化工作。

## 卡点

- 能按采购案例回答五题，但实际框架怎样建图或部署耐久后端不是完整代码教程，本报告明确未运行框架。
- checkpoint、pending writes、事件重放、Activity 重试分别对应不同边界，阅读时需要反复回到“什么已经确认、什么可能重做”，不能把它们统称为从某行继续。
