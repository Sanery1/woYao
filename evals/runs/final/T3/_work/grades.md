# T3 独立评分

评分来源仅为 grading-packet.json 中本主题的题干、预先固定金标及双轮读者对应题回答与直接引文。未读取报告或其他评分，未从主线复述补分。

规则：2 分为全部固定要点；1 分为至少一半要点（奇数项向上取整）；0 分为其余或整题明确“报告未说明”。部分答出、部分未说明时按实际命中评分；等效表述接受，未完整表达的复合要点计为缺失。

### 第 2 题：2/2

题干：进程在"工具已经调用成功、checkpoint 还没写入"的时候崩溃，恢复后会发生什么？

命中：从上一个 checkpoint 恢复；如果恢复机制重试未完成步骤，这一步可能重新执行；外部动作可能重复，须幂等或核验

缺失：无。

对应答案/直接引文：

> 新进程看到的还是旧状态……可能把工具步骤再执行一次……按原幂等键去重……否则……重复创建订单……未知并核对。

报告缺口（仅按该题回答可确认）：本题无可据回答确认的缺口。

### 第 3 题：1/2

题干：为什么说 checkpoint 本身不能保证外部副作用"恰好执行一次"？

命中：外部调用和写 checkpoint 不是同一个原子操作；两者之间可能崩溃

缺失：checkpoint 单独不保证恰好一次；至少一次还要求可靠重试和最终恢复

对应答案/直接引文：

> 外部系统提交和本地 checkpoint 提交通常不是同一个事务……崩溃窗口……业务效果是否唯一还要由稳定身份和目标系统约束。

报告缺口（仅按该题回答可确认）：未说明“至少一次”也依赖可靠重试与最终恢复，第 3 固定要点不完整。

### 第 4 题：2/2

题干：为"发起付款"这样的步骤设计一个防止重复执行的方案。

命中：使用幂等键（由运行 id 和步骤确定，重试时复用）；由服务端按幂等键去重；或在恢复时先查询外部状态，确认是否已执行

缺失：无。

对应答案/直接引文：

> 同一笔业务付款……稳定 operation_id/幂等键……首次和重试都使用原键……付款服务必须按键去重……按原键查询或重试。

报告缺口（仅按该题回答可确认）：以同一业务付款稳定身份作为运行/步骤固定键的等效表述；本题无缺口。

### 第 5 题：2/2

题干：什么时候应该把一个大步骤拆成多个小步骤，分别做 checkpoint？代价是什么？

命中：步骤包含多个昂贵或有副作用的操作时拆分；拆分后崩溃时需要重做的范围更小；代价是写入次数和存储增加、状态设计更复杂

缺失：无。

对应答案/直接引文：

> 昂贵计算、有副作用的动作……失败可能重跑前半段……更多调度、持久记录、序列化、存储、提交延迟和结构复杂度。

报告缺口（仅按该题回答可确认）：本题无可据回答确认的缺口。
