## 主线复述

模型返回的是工具请求，真正执行函数的是 Python 宿主。宿主验证名称和参数，将模型的请求与对应工具结果按调用标识放回历史，再请求模型。合法工具请求的参数错误可以作为结果反馈，协议损坏或传输失败则停止。循环在正常文本结束时完成，并用最大模型请求轮数防止持续调用。报告给出完整代码和本地 mock 验证，真实 provider 尚未验证。

## 五题作答

1. 初始是 system 约束和 user 问题；收到工具请求后，先追加带 tool_calls 的 assistant 消息，再为每个调用追加带 tool_call_id 的 tool 结果；下一次请求模型后，正常结束的 assistant 文本成为最终消息。支持：§2“先把模型的 assistant 消息放回历史，再执行工具，追加”及 §4 的 run。
2. arguments 是 JSON 字符串，外层响应解析后仍要 json.loads 一次；执行前还要验证函数白名单、字段集合、类型、数值范围，并核验调用结构和标识。支持：§2“arguments 本身是字符串”，§4 execute 与“程序仍在 execute 验证”。
3. 没有工具调用、finish_reason 是 stop 且有非空文本时正常返回。协议不完整或传输异常会报错；max_turns 耗尽也停止，因为模型可能不断请求同一工具。支持：§4 的 if not calls 分支，§6“最多请求模型六次，然后抛出预算耗尽”。
4. 参数错误作为 ok=false 的工具结果回去，模型下一轮才有机会纠正或向用户说明失败，不能保证必然纠正。不是所有错误都这样处理：缺失调用标识无法配对，或网络没拿到有效响应时，应停止并报告。支持：§4“模型下一轮能够据此纠正或说明失败”及 §6 的数量为 0 与网络超时例子。
5. 依据现有代码可推得：给 TOOLS 增加名称、描述和参数 schema；在 execute 白名单分发中增加读文件分支、参数验证及实际读取；给它的成功和错误补充本地验证。run 已按各调用 id 通用回传，正常协议下不需为每个新工具重写循环。支持：§4“第一处看 TOOLS”“execute 先比较函数名，再解析参数”和“数量从一变成二，不需要修改循环结构”。但报告未说明读文件工具的具体目录权限、路径处理和返回量契约，不能直接从本文得到可用的读文件实现。

## 卡点原句与原因

- “本例只有 quote，因此模型即使请求 shell 也只得到 unknown_tool”：白名单原理清楚，但 execute 把名称验证、参数验证和计算写在一起；新增读文件时需要自行设计分发和文件边界，文中没有完整迁移示例。
- “如果没有启动本地服务，连接被拒绝是预期现象”：能理解这个错误，但本报告没有给出把 mock 作为交互服务单独启动的命令；照抄 agent.py 后先运行测试更明确。
