# T2 独立模拟读者第 1 轮

读者档位：B（会代码，首次接触 Agent 循环）。仅依据题干及 `reader-copy.md` 回答。

副本 SHA256：`1D492F0459BC14FC5D686D9C86A4E300804BA1ACD4EE0C291C60D672BF11EADF`

## 主线复述

模型产生工具请求，Python 宿主检查并执行工具，结果进入消息历史后再次请求模型。
工具定义让模型知道能请求什么，实际执行仍由宿主白名单和参数检查决定。
每个工具结果用调用标识对应原请求，历史必须保留原 assistant 工具消息。
参数失败可回传给模型，消息协议破损或网络失败则有明确错误出口。
正常回答与轮数预算是不同结束方式，本地 mock 通过并不代表真实服务已经验证。

## 逐题回答

### 1. 一轮带工具调用时，消息依次追加什么？

原回答：初始历史有 system 和 user；模型返回工具请求后，先追加完整的 assistant 消息，其中保留 tool_calls，再为各个调用追加 role=tool 的结果，用各自的 tool_call_id 关联。随后将这些历史发给模型；正常结束时再形成最终 assistant 文本。多个工具结果不能都随意写成一个调用 ID。

支持：§2“先把模型的 assistant 消息放回历史，再执行工具”；§4 run 代码先 append assistant，再循环 append tool，最终返回附上 assistant 文本的历史。

### 2. arguments 是什么类型，执行前如何处理？

原回答：arguments 是字符串，内容是 JSON；外层响应解析以后，仍要再用 json.loads 解析这段字符串。然后按白名单检查工具名，确认参数是期待的对象、字段齐全且无多余字段，并检查类型和范围。不能直接 eval，也不能按模型给出的名字随意导入执行。

支持：§2“arguments 本身是字符串”；§4“名字白名单决定能做什么；schema 决定期待什么；Python 检查决定本次输入是否真的可用”。

### 3. 循环何时结束，为什么要最大轮数？

原回答：没有工具调用、finish_reason 为 stop，而且 content 是非空字符串时，正常返回最终文本；没有工具请求并不自动代表成功，截断等情况会报错。持续请求工具会耗尽 max_turns，本例最多六次模型请求，用来阻止循环一直继续。协议错误和传输错误也会停止；这个轮数上限并不能精确限制费用。

支持：§4 run 的 stop/content 检查；§6“模型也可能不断请求同一个工具”“这个上限不能精确约束费用”。

### 4. 工具出错为什么回传结果而非直接抛异常？

原回答：对于一次能识别归属的合法工具请求，把参数失败写成 ok=false 的工具结果，模型下一轮才能看到原因，并可能纠正参数或向用户说明失败；直接退出就没有这次反馈机会。但报告没有要求所有错误都回传：缺失调用标识时无法正确配对，网络超时也不是报价工具失败，这些会停止并报告。

支持：§4“模型下一轮能够据此纠正或说明失败”；§6“不能把‘请求失败’当成一个报价工具错误硬塞回对话”。

### 5. 新增“读文件”工具要改哪里？

原回答：依据现有代码结构，我能推到两处必改：在 TOOLS 增加读文件的名字、描述和参数 schema；在 execute 增加允许的名字分支、对应参数校验与真正的执行逻辑。现有 run 已按调用 ID 通用地追加结果，request_model 已统一发送 TOOLS，报告没有显示它们需要为每个工具单独加分支。报告未说明读文件工具的完整实现、可读范围或读取失败应怎样定义，所以不能从本文直接抄出可用的读文件方案。

支持：§4 TOOLS、execute、request_model 和 run 代码；§6“真正可执行的能力仍由宿主白名单控制”。新增工具的两处改动是按报告代码作出的迁移推断，正文没有提供读文件示例。

## 卡点
