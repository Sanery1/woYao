# 独立读者第 2 轮：T4

读者档位：A，不写代码的产品人员。仅依据题干与本份报告作答，未使用外部知识。

报告副本 SHA256：`BC7500B7F146BE4EDDD556F19CFD53F4396DBB40AF5C9BB3EE1BEA8DC9E55647`

## 主线复述

模型接着已有文本预测下一个 token，需要从历史里取相关信息。KV cache 留住各层历史位置算过的 K 和 V，避免重复生成这些中间结果，但仍要读取历史。缓存会随实际保留的输入、输出和活跃请求总长度增长，所以模型能装下不代表多会话也装得下。分页、前缀复用、量化或迁移缓存解决不同开销，要按质量、延迟和成功问答成本验收。

## 五题作答

1. 因为下一个 token 是依据已有文本预测的，当前位置的注意力需要判断从哪些历史位置取信息；例如写“保修期限为”之后仍需从手册找相关内容。支持：§1“它依据已有文本预测下一个token”与“当前Q仍然要与历史K匹配，再汇集相应V”。报告说可能需要参考更多历史位置，不等于每个位置都同样重要。
2. 会反复计算已经处理过的历史位置的 K、V；缓存把这些结果保留，后续只补新增位置所需的部分。支持：§1“缓存省下的是反复生成历史K、V的工作”。
3. 缓存的是各层历史位置的 K 和 V，前者用来与当前需求匹配，后者提供汇集的内容，都是数字而非摘要。报告说明“当前token产生Q”，却未直接解释为什么旧 Q 不再需要、为何不缓存 Q；这个为什么的完整答案，报告未说明。
4. 随所有活跃请求实际保留的 token 总数增长，输入和已生成输出都要算；同样长度下活跃请求数翻倍也会翻倍。每 token 占用还取决于层数、KV 头数、每头数字个数和每个数字字节数，K、V 各一份。支持：§2“总缓存token数T是所有活跃请求实际保留长度之和”，以及公式“2 × L × H × D × S × T”。
5. 同张卡的显存还要放共享模型参数与运行空间，每个活跃请求又通常单独保存上下文缓存；对话变长和活跃请求增多会一起挤占剩余容量。可减少无关输入、限制输出或活跃请求，或根据瓶颈采用分页、重复前缀复用、KV 量化、迁移至 CPU；模型结构中的 GQA 也会影响容量，但文中说不能随意切换。支持：§2“三笔”预算、§3“长度、并发都加”示例和 §4 三种优化。仅“在线”不保证占有 KV，报告限定为实际保留与执行的活跃请求。

## 卡点原句与原因

- “当前token产生 Q（查询向量），表达‘现在需要什么’”：能用这个比喻理解 Q 的作用，但文章没有补上历史 Q 为何不再使用这一步，第三题只能答出缓存内容。
- “同样的参数总量，KV头数可能不同；不能拿查询头数直接代替KV头数”：对产品人员仍较抽象，好在文章随后把它落到“让工程师给每token缓存多大”，无需先掌握头的具体计算。
